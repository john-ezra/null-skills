# Design moves

Each move ends with its counterweight, *Too far*. When moves conflict, pick the structure with the best information hiding, the fewest dependencies, and the deepest interfaces. A named pattern is a prebuilt design: reach for it when the problem already has that shape, never bend the problem to fit it, and count it as interface spent like any structure of your own.

For module depth, information hiding, seam placement, and the over-deepening brake, apply [MODULE-DESIGN.md](MODULE-DESIGN.md) before the moves below.

## Somewhat general-purpose

The module's functionality reflects today's needs; its interface doesn't (`insert(position, text)`, not `backspace(cursor)`). The payoff is a simpler, deeper interface now, not reuse later: a general interface wins even if it only ever has one caller. Three questions:

- What is the simplest interface that covers all my current needs? Fewer methods is only progress while each method's use stays simple, trading methods for extra arguments simplifies nothing.
- In how many situations will this method be used? A method shaped around one caller's one purpose has absorbed that caller's concepts.
- Is this easy to use for my current needs? When callers must write loops or scaffolding for the obvious thing, the interface is missing functionality it should own, and a per-item call also costs performance the module could have batched.

Expect the general interface to cost a few more characters at each call site and fewer lines overall; the call site becomes obvious because the behavior is spelled out where the reader is. Decide who needs to know each detail: a method that hides a detail its caller's logic depends on is a false abstraction, callers read the body anyway and the hiding only adds obscurity, so such a detail belongs in the caller's code where it is visible.

*Too far:* so general it's awkward for the need in front of you. The third question catches it, and the fix is a range or batch operation inside, never a special-purpose method for that one caller.

## Pull complexity downward

Most modules have more users than developers, better for one implementer to suffer than every caller. Handle the hard cases inside; a simple interface outranks a simple implementation. Pull complexity down when all three hold: it is closely related to the module's existing purpose; it removes complexity from many places above; it simplifies the module's interface. Configuration parameters move complexity *up*: before exporting one, ask "will the caller or a higher layer determine a better value than we can compute here?", computing it also keeps it current as conditions change; a parameter you must export gets an automatic default, and each one you export is a part of the problem the module left unsolved.

*Too far:* pulling down knowledge that belongs to the caller (a UI key binding into the text store) hides nothing and concentrates leakage, the limit case being the whole application in one class; and a computed default still needs an override path, behind a separate method the common caller never meets, wherever a real minority needs the other value.

## Define errors out of existence

An exception here is any uncommon condition that diverts the normal flow: a thrown object, an error value, a null or sentinel return, a Result error. Each one is part of the interface and counts against every interface it propagates through, not only the thrower's, so a class with many is shallower than one with few, and the handling code is where the complexity, and, per the study Ousterhout cites, over 90% of catastrophic distributed-system failures, lives. Throwing is easy; handling is hard; detecting more is not better, since each rejection you add is a handler someone above must write, and a difficult situation punted to the caller usually finds a caller with no better idea what to do. Every recovery invents failures of its own (a resend can deliver twice, the backup copy can be missing too); follow each chain until it ends in a handler that raises nothing new. Define away first; what remains gets one handler wherever it catches the most, low or high; what is not worth handling crashes:

1. **Redefine semantics** so the error can't occur: `unset` means "ensure the variable no longer exists" (calling it on a missing variable is success); substring of an out-of-range span returns the overlapping characters; deleting an open file removes the name now and the data when the last user closes it. The objection that throwing catches bugs is answered by the code callers add to dodge the throw, or forget to add; fewer special cases means fewer bugs.
2. **Mask low**: detect and handle at a low level so nothing above ever sees it (TCP resends dropped packets; nobody above TCP handles packet loss).
3. **Aggregate high**: one handler far up the stack catches a whole family, a request-abort exception thrown anywhere, caught once at the dispatch loop, its message composed where it was thrown. The catch site restores consistent state before the next request, an abort that leaves half-applied changes is a second failure, and the abort type stays distinguishable from errors fatal to the whole process so the loop handler never swallows those. Promote rare small errors into a larger failure you must already recover from (a corrupt object crashes its server; server recovery restores it), so there is one recovery path and it runs often enough to be trusted.
4. **Crash** on errors not worth handling, out of memory, corrupt internal structures: print diagnostics and abort, through one wrapper so no caller ever checks. Whether crashing is acceptable depends on the application: a replicated store must recover from the I/O error a text editor may die on.

The first rung applies to special cases too: design the normal case to subsume them, a selection that always exists, possibly empty, needs no "no selection" code anywhere. A distinction the user sees need not exist inside; it becomes the empty value of the normal case, a different layer with a different abstraction.

*Too far:* define away or mask only what no caller needs to know. A caller that must react to the failure (a lost message, a dead peer) gets the exception whatever it costs the interface; the rare caller that merely wants to know gets a separate query (does the variable exist?), not an exception on everyone's path. Crash only where the application may die, and promote only errors rare enough that the big recovery's cost stays invisible.

## Together or apart

Judge every split by total complexity, and remember splitting itself costs: more pieces to track, more interfaces (every interface is complexity), management code, related code moved apart, duplication. Bring code together when: it shares knowledge (two places that both know a format); it is used together in both directions; it overlaps conceptually under one simple category; one piece can't be understood without the other; or the join removes an interface whose only job was to hand one piece's result to the other, the merged module then doing unasked what callers used to wire up between the two. A merge callers still drive piece by piece bought nothing, and one whose state needs a flag to say which piece is which cost something: split again and look for the smaller general type both pieces were built from. Keep a general-purpose mechanism apart from its special-purpose uses, pull the special code up into the layer that owns the purpose, leave the mechanism general below (the undo history list below; text-specific undo entries above; the policy for when to group them higher still, in the code that owns the user-visible behavior). The separation is per mechanism: one general mechanism per module, so a second unrelated one gets its own class, but special-purpose code for one mechanism sits beside the general code of another when the two are closely related, which is why the text store holds its own undo entries and not the history list.

Methods: each should do one thing and do it completely. Length alone is rarely a reason to split, a several-hundred-line method with a simple signature that reads top to bottom is deep, which is good, and the more the blocks inside interact, the more they belong in one method where a reader sees them together. Split only (a) by factoring out a cleanly separable subtask, readable without knowing the parent, the parent without the child's internals, and plausibly useful to a second caller, or (b) into two caller-visible methods, only when the original conflated unrelated things and most callers will need just one. Join when it turns two shallow methods into one deep one, deletes a structure that existed only to pass results between them, or moves knowledge held in both into one; if understanding one half now requires reading the other, the split failed, rejoin.

*Too far:* apart is right only for pieces that are truly independent. Two caller-visible halves that hand state to each other, or a helper read only together with its single call site, is the over-split.

## Compose before inheriting

Interface inheritance, one signature with several implementations, is leverage: the interface is learned once. Implementation inheritance shares state and default bodies between parent and child, so a change to either means reading the other, which is information leakage inside the hierarchy. Prefer composition: the shared behavior becomes a helper class the would-be subclasses hold. When a base class with shared code is unavoidable, the parent owns its instance variables, and subclasses reach them read-only or through the parent's methods, never by writing them directly.

*Too far:* a helper whose every method the owner forwards unchanged has rebuilt the hierarchy as a pass-through layer; when several implementations share one body and no state, a base class holding that body and nothing else is the smaller interface.

## Different layer, different abstraction

Every element of design infrastructure, interface, argument, function, class, layer, is complexity spent, and must eliminate more complexity than its existence adds. When an operation passes through adjacent layers without the abstraction changing, one layer isn't paying rent. An interface that mirrors the storage representation makes every caller do the module's work: a character-oriented interface over line-oriented storage is functionality, a line-oriented interface over line-oriented storage is not. Before writing a decorator, ask in turn: does the feature belong in the underlying class (it is fairly general, logically related to it, or most users will want it); does it belong in the one use case that needs it; can it join an existing decorator so one deeper decorator replaces several shallow ones; can it stand alone without wrapping the base at all? State threaded through every signature between top and bottom goes first into an object the top and the bottom already share, and failing that into a context object, one per instance of the system, holding all of that instance's global state, passed only to constructors and stored by the objects that need it, fields immutable once built, tests building a different context rather than mutating one; not into a module-level global, which avoids the threading but forbids two instances of the system in one process, which tests need.

*Too far:* a context is a global-variable bag; admit only per-instance state that would otherwise be threaded or global and say why each field exists, or it becomes a grab-bag whose entries nobody can explain and whose dependencies nothing marks. Same-signature methods that sit in one layer and never call each other are implementations of one interface, not layers to collapse.

## Naturally efficient

Neither tune statements nor ignore cost: a system that never weighed performance runs several times slower than it needs to, with no single place to fix. Know what is expensive, a network round trip, a storage read, a dynamic allocation, a cache miss, each worth hundreds to millions of instructions, so a design that adds one per call is a different design. When two designs are equally simple, take the faster on sight: a hash table over an ordered map unless the order is used, values inline in an array over an array of pointers. When speed costs complexity, pay only when the cost is small and hidden behind the interface, or when measurement already shows this path matters; otherwise ship the simple design and optimize on evidence.

Before changing code for speed, measure deep enough to name the few places where time goes, record the baseline, and re-measure after; revert anything that did not measurably help unless it also made the code simpler. Look first for a fundamental fix, a different algorithm or a cache, before restructuring code paths. As a last resort, design around the critical path: write the smallest code that could serve the common case as if structure and special cases did not exist, then find the cleanest design that stays close to it, with one test at the top that detects every special case, no further branches on the path after it, and the special-case code off the path written for clarity, not speed.

*Too far:* speed bought with complexity in the interface, or with tuning no measurement demanded. Simple code with special cases defined away and few layer crossings is usually fast already; look there before adding a fast path.

## Model the domain before the control flow

Two flags valid only in certain combinations, one shape test copied into several files, or a chain of branches that walks one concept through its states: each is a domain concept simulated by control flow. Give the concept a structure of its own, a closed union, a state machine, a registry, a reducer, a collection built for the purpose, or a constructor that refuses the invalid combinations, so the rule lives in one declaration and callers stop re-deriving it. The structure pays for its interface when it retires repeated rules, impossible combinations, or facts callers had to carry; conditionals relocated into a table are the same complexity at a new address.

In a typed language, ask the same of the types: two meanings sharing one primitive, a hand-copied version of a schema that lives elsewhere, a cast covering a partial case, or a closed set of variants a switch can silently miss are each a modeling gap. Precision in a type is worth keeping while it prevents a real misuse or spares the reader a lookup, and not beyond.

*Too far:* a shape that is clear and local, three branches in one function the reader sees whole, gains nothing from a union or a table; the new structure is interface spent on complexity that was already contained.

## Give mutable state one owner

Settle the data before the interface: what the model holds, which reads dominate, and which single actor may write each piece. Several writers converging on one file, key, branch, or object usually turn out to be recording separate facts, and the fix is a target per writer with the merge done wherever the facts are read together, not a shared record everyone edits. Where a single value genuinely must hold across writers, the guarantee has to be a structure the code enforces, one writer, a phase that runs alone, a lock, a transaction, a compare-and-swap; a comment or a prompt asking the actors to coordinate enforces nothing.

*Too far:* a value whose parts form one invariant, a balance and the ledger behind it, cannot be split into per-writer targets; the split moves the race to the read seam and adds a merge nobody can make correct.

## Parse external representations at the seam

Whatever arrives from outside the process, a configuration file, a command line, a request body, a stored blob, a framework's request object, is a representation someone else chose. Convert it exactly once, in the adapter at the outermost seam, into the internal type that says what the program actually knows, and let only that type travel inward. Transport failures and framework plumbing stay in the adapter too, surfacing only when a caller has a decision to make about them.

Letting a wire, database, or framework type stand as a module's interface to save writing an adapter hands every caller the representation, so the representation's next change reaches all of them across the seam. Generate internal types from a shared schema only where the two sides are meant to hold the same knowledge, a contract both publish to each other.

*Too far:* validating the same input again inside, behind a seam that already narrowed it, buys a second copy of the rules and nothing else; deriving internal types from a schema the other side does not actually share turns an accidental match into a dependency.

## Make state changes converge

Any operation that mutates, a command, a lifecycle step, the body of a retry loop, is designed for two runs: the one that starts clean, and the one that follows an attempt that finished, half-finished, or died. Write it as reconciliation toward the state you want rather than as a script that assumes nothing is there yet: on start, keep what is already correct, delete what is demonstrably left over, rebuild what is missing, and judge staleness by identity or content, never by which artifact came first.

Swallowing an already-exists error does not make an operation repeatable; the test is whether a second execution, from any partial state, ends in the same correct observable result as the first.

*Too far:* an operation whose repetition is the point, appending a ledger entry, sending each notification, must not be made to converge; and reconciliation that costs more than the retry it prevents belongs behind a plain retry.

## Pin behavior before structural movement

A refactor that promises to change nothing observable has to say what counts as observable before any code moves: write down the contract callers rely on and the smallest check, a golden output, a differential run, an interface-level assertion, that would fail if the moved code drifted from it. That pin earns a permanent place in the suite only when it defends an observable contract; otherwise it is disposable, deleted once the movement is done. A question prose cannot answer, how a library really behaves, what a layout costs, where the time goes, gets an isolated throwaway prototype, and only the measured answer comes back into the design.

*Too far:* a pin fastened to internals, call order, private state, exact log lines, fails on the very restructuring it was meant to permit and defends nothing a caller can see.

## Names

Precision plus consistency. Image test: from the name alone, no declaration, no doc, how well does a reader guess the referent? Two or three words at most, chosen to say what the thing is and, just as usefully, what it is not. Booleans are predicates (`cursorVisible`, not `blinkStatus`). Generic `i`, `j` only in loops short enough to see whole, `i` outer, `j` inner. A name can also be too specific: a parameter named for what one caller passes (`selection` for any range) promises more than the method requires, so name it for what the method accepts. One name per concept everywhere, that name for nothing else, and the concept narrow enough that every holder behaves alike, `fileBlock` and `diskBlock`, never one `block` for both; when one method holds two of the same thing, keep the common name and prefix each (`srcFileBlock`, `dstFileBlock`) rather than inventing a second. A very short name passes only where the project uses it for exactly one concept everywhere; the same short name for several concepts is the `block` mistake with fewer letters. The greater the distance between declaration and use, the longer the name. When a precise, intuitive name won't come, the entity is unclear, refactor the entity, not the thesaurus.

*Too far:* a four-word name, a parameter named for one caller's guarantee, or a spelled-out index in a three-line loop. Readers, not the writer, decide what is cryptic; a name the project uses consistently for one concept is not.

## Comments

Comments capture what was in the designer's mind but can't be represented in code; without them a method's only abstraction is its declaration, and a method whose users must read its body has no abstraction. Every comment states something a first-time reader could not get from the code beside it. Every class, every method, every member variable gets one, in the format the project's documentation tool consumes (Javadoc, Doxygen, godoc, docstrings); where the project has none, borrow a similar language's convention rather than inventing one. A method comment opens with one or two sentences of behavior as callers see it, then each argument and the return value with their constraints and dependencies on each other, every side effect (any consequence outside the result that changes later behavior, including stored state and written files), every exception that can escape, and every precondition that survived an attempt to remove it. A class comment states the abstraction, what one instance represents, and the limits a prospective user must know such as threading, with no internals and no per-method detail; a short usage paragraph is added only for a deep class whose methods combine in a non-obvious order.

Comment at a different level than the code: lower for precision, units, inclusive/exclusive bounds, meaning of null or of a missing entry, who frees the resource, invariants; describe what the variable *is* (nouns), not how it's manipulated (verbs), or higher for intuition, found by asking what the code is trying to do, what one sentence explains all of it, and what matters most, so the reader can judge whether the code does everything the goal needs; and for handlers and any method reached only in unusual situations, when and why it is invoked. When either level would serve, prefer the higher one; abstract comments survive edits that falsify detailed ones.

Interface comments serve callers only and sit beside the method's body, not in a separate header or declaration file: readers get interface docs from tooling, and only a comment the editing developer sees gets updated. Implementation notes live in the body, each pushed to the narrowest scope covering what it describes, with a short overview of the phases at the top still welcome. Most bodies need none, the interface comment already says what a short method does; a long method gets one comment before each major block and, for a loop whose body is not obvious, one sentence on what an iteration does, short loops none; a well-named local whose uses sit within a few lines gets none, one used across a long span gets a line saying what it holds; code added for a bug fix whose purpose is not evident gets a why, citing the ticket rather than retelling it. The farther a comment sits from the code it describes, the more abstract it must be, so ordinary edits do not falsify it.

Document each design decision exactly once, where developers will actually look: in the code, never only the commit log; a call site never explains the callee, that is the callee's interface comment. A cross-module decision goes at the choke point every such change must pass through, as a note listing every other site the change touches, placed where the next addition will land; with no such point, a single central design-notes file, one labeled section per topic, with a one-line pointer from each dependent site. Information already documented elsewhere, spec, RFC, manual, gets a reference, not a copy. A missing or vague comment is obscurity: file the finding under cognitive load or unknown unknowns, never change amplification.

*Too far:* a comment on every line, a body comment in every short method, a loop comment on a short loop, or a class comment that recounts each method restates the code; exactly-once permits a pointer to the master copy and a reference to outside documentation; and the central design-notes file is the last resort, since distance from the code makes it drift.

## Consistency

Similar things look similar; different things look different, the payoff is that "if it looks like an x, it is an x" stays a safe assumption. Consistency runs at every level: names, style, one interface reused by several implementations, a familiar pattern, and the invariants a structure always holds; an invariant is a convention at the data level, stated once where the structure is declared, and every special case it removes is removed for every reader. Follow existing conventions on sight; before making a design decision, look for where the project already made it and match. A convention you introduce is written down where the next developer will see it, a project-wide one in the style guide or contributing doc, a local one in a comment at the code it governs. Break an established convention only when you have significant new information *and* the new way is worth converting every old use so no trace of the old convention remains *and* the user has agreed to the conversion; a better idea alone is not sufficient excuse, and reconsidering settled conventions is rarely worth the time.

*Too far:* forcing different things into one shape, one name for two concepts, a pattern the problem does not fit, is inconsistency wearing consistency's clothes; "if it looks like an x, it is an x" then fails, which is worse than having no convention.
